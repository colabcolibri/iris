# Internacionalização (i18n)

## Objetivo

Internacionalização PT/EN do produto Iris com traduções organizadas por **domínio** (SRP), provider único no admin React, formatação locale-aware e erros da API expostos como **códigos estáveis** traduzidos no client.

Escopo v1.20: locales `pt` e `en` na UI. O agente LLM continua usando `response_language` (15 idiomas) — escopo distinto, fora deste doc.

## Locales suportados

| Locale app | BCP 47 (Intl/HTML) | Default | Persistência |
| ---------- | ------------------ | ------- | ------------ |
| `pt` | `pt-BR` | sim | `localStorage` key `iris-locale` |
| `en` | `en-US` | — | idem |

Regras:

- Admin autenticado: operador escolhe locale no switcher; valor persiste entre sessões.
- Landing: rota define locale (`/` → `pt`, `/en` → `en`); alinhado com `i18n/routing.ts`.
- Demo: herda `iris-locale` quando possível; troca no demo reseta fixtures (`resetDemoState`).
- `document.documentElement.lang` atualizado pelo provider (como `LandingI18nProvider` hoje).

## Domínios de tradução

Cada domínio = um bounded context de copy. **Proibido** monolito `messages.json`. Padrão: objetos TypeScript tipados + arquivos `pt.ts` / `en.ts` por domínio.

| Domínio | Path | Responsabilidade |
| ------- | ---- | ---------------- |
| `shell` | `admin/src/i18n/domains/shell/` | Nav, login, header, confirm global, language switcher |
| `labels` | `admin/src/i18n/domains/labels/` | Status posts/comentários, reply modes, audit stages, badges enum |
| `posts` | `admin/src/i18n/domains/posts/` | Calendário, kanban, lista, post dialog, upload |
| `comments` | `admin/src/i18n/domains/comments/` | Hub comentários, thread, reply composer, import |
| `messages` | `admin/src/i18n/domains/messages/` | Inbox DM, thread, activity hub, janela 24h |
| `settings` | `admin/src/i18n/domains/settings/` | Settings cards, MCP, LLM, auto-reply toggles |
| `agent` | `admin/src/i18n/domains/agent/` | Persona forms, simulador, execuções |
| `products` | `admin/src/i18n/domains/products/` | CRUD produtos |
| `webhooks` | `admin/src/i18n/domains/webhooks/` | Event log UI |
| `legal` | `admin/src/i18n/domains/legal/` | Privacy policy body |
| `marketing` | `admin/src/i18n/domains/marketing/` | Landing (migrado de `i18n/landing/`) |
| `demo-content` | `admin/src/i18n/domains/demo-content/` | Fixtures editoriais demo (migrado de `demo/fixtures/i18n/`) |
| `server-errors` | `admin/src/i18n/domains/server-errors/` | Mapa `code` → mensagem user-facing |
| `server-email` | `server/src/i18n/email/` | Assunto/corpo OTP e contact (server-side) |

Tipagem: cada domínio exporta interface `XxxMessages`; `pt.ts` e `en.ts` satisfazem `satisfies XxxMessages`. Composição no provider — não re-export flat de todas as keys.

## Admin — provider e layout de pastas

```
admin/src/i18n/
  types.ts                 # AppLocale, APP_LOCALES, DEFAULT_LOCALE, localeToBcp47()
  storage.ts               # read/write iris-locale
  provider.tsx             # AppI18nProvider
  hooks.ts                 # useAppLocale(), useMessages('shell'), etc.
  compose.ts               # merge domain modules for active locale
  formatting.ts            # Intl wrappers (see § Formatação)
  domains/
    shell/{types,pt,en}.ts
    labels/{types,pt,en}.ts
    ...
```

Provider monta em `App.tsx` **acima** de rotas admin, landing e demo (substitui contexts paralelos na US-0209):

```txt
AppI18nProvider
  ├── Landing routes (marketing domain)
  ├── Admin ProtectedRoute → AppLayout
  └── DemoModeProvider → DemoAppLayout
```

API pública (implementação US-0197):

- `useAppLocale()` → `{ locale, setLocale, bcp47 }`
- `useDomainMessages('shell')` → objeto tipado do domínio
- Reutilizar padrões de `landing-context.tsx` e `demo-locale-context.tsx` sem terceiro union de locale.

**DRY:** `lib/status.ts`, `comment-status.ts`, `reply-audit-labels.ts`, `reply-mode-options.ts` passam a consumir domínio `labels` — não duplicar maps por page.

## Formatação (Intl)

Módulo único `admin/src/i18n/formatting.ts`:

- `formatRelativeTime(date, locale)` — substitui `pt-BR` fixo em `lib/format-relative-time.ts`, `lib/message-time.ts`, etc.
- `formatShortDate`, `formatDateTime`, `formatNumber` — usam `localeToBcp47(locale)`.

Regra: **nenhum** `"pt-BR"` literal em helpers migrados; formatação ≠ copy domain (SRP).

Server `domain/time/zoned-datetime.ts` permanece server-side; UI formata no client com locale ativo.

## Erros da API

**Decisão:** códigos estáveis no JSON + tradução no client (`server-errors` domain). Server **não** traduz por `Accept-Language` na v1.20.

### Shape de resposta

```json
{
  "error": {
    "code": "META_TOKEN_EXPIRED",
    "details": { "reason": "token_expired" }
  }
}
```

Compatibilidade: respostas legadas `{ "error": "string" }` tratadas no client como `code: "LEGACY_MESSAGE"` com fallback à string (fase de migração).

### Server

- `ValidationError` evolui para aceitar `code: string` (constructor ou factory `validationError(code, details?)`).
- Erros de domínio user-facing (`MetaNotConnectedError`, rate limits, contact form) emitem `code` estável; remover strings PT do payload JSON.
- Catálogo de codes: `server/src/domain/errors/error-codes.ts` (constantes SCREAMING_SNAKE).
- `map-http-error.ts` sempre usa `sendApiError(res, status, code)` — **message field removido** para erros migrados.

### Admin

- `lib/api-error.ts`: parse `{ error: { code, details? } }`.
- `translateApiError(code, details?, locale)` → string via domínio `server-errors`.
- Toasts e form errors chamam `translateApiError` — nunca `err.message` direto para erros de API.

Codes iniciais (expandir na US-0207):

| Code | HTTP | Origem |
| ---- | ---- | ------ |
| `VALIDATION_FAILED` | 422 | ValidationError genérico (fase 1) |
| `META_NOT_CONNECTED` | 422 | MetaNotConnectedError |
| `META_TOKEN_EXPIRED` | 422 | meta readiness |
| `PUBLISH_NOT_CONFIGURED` | 503 | PublishNotConfiguredError |
| `RATE_LIMITED` | 429 | Meta conversations rate limit |
| `CONTACT_INVALID` | 422 | contact form validation |

## Email transacional

Templates em `server/src/i18n/email/{login,contact}/{pt,en}.ts`. Layout compartilhado `domain/email/email-html.ts` recebe `lang: 'pt-BR' | 'en'`.

Resolução de locale:

| Fluxo | Locale |
| ----- | ------ |
| OTP login admin | header `X-Iris-Locale: pt\|en` no `POST /api/auth/login` (admin envia locale ativo) |
| Contact form landing | campo `locale` no body (`pt` \| `en`) — landing já conhece rota |
| Default | `pt` |

OTP numérico não é traduzido. Assunto + corpo HTML usam strings do módulo `server-email`.

## Migração landing e demo

Fase 1 (US-0197–0200): novo provider convive com contexts antigos.

Fase 2 (US-0209):

1. Mover `i18n/landing/{pt,en}.ts` → `domains/marketing/`.
2. Mover `demo/fixtures/i18n/*.en.ts` → `domains/demo-content/` (PT como `pt.ts`, não overlay-only).
3. `LandingI18nProvider` / `DemoLocaleProvider` viram thin wrappers sobre `AppI18nProvider` ou são removidos.
4. Deprecar `LandingLocale` separado — usar `AppLocale`.

Referência estado atual: `docs/architecture/admin-demo-mode.md` — § i18n do demo.

## Segurança e barreiras

- Barreiras crisis/CVV 188 condicionadas a `pt-BR` no agente (`02_security.md`) — **não** alteradas por locale da UI.
- `server-errors` não expõe stack ou secrets em `details`.
